Módulo de paciente
Interfaz adaptable a teléfono móvil

Entrega del 7 de octubre de 2026. Código de la rama de trabajo actual, incluidos los cambios de diseño pendientes de commit. Consulte VERSION.json para el commit de base y INVENTARIO.json para la versión exacta de cada archivo.

Destino: Android nativo, Flutter o React Native. El módulo actual es una interfaz web en Laravel Blade + HTML + CSS + JavaScript. Para conservar su diseño y comportamiento, hospede el módulo en Laravel y abra /patient desde un WebView. Para una interfaz enteramente nativa, reutilice los recursos y la API, y traduzca las pantallas y sus estados a componentes de la tecnología elegida. Este paquete no es un APK ni un proyecto Flutter/React Native compilado.

Qué incluye la pantalla actual

  • Inicio: publicaciones, historias y acciones sociales.
  • Comunidades: buscador, historias, directorio, detalle, clases, eventos y reservaciones.
  • Registro: parámetros de bienestar, entradas manuales, favoritos y archivos adjuntos.
  • Mi Salud: parámetros e historial clínico con el fondo abierto y los controles móviles actuales.
  • Calendario: Comunidades/Salud, Próximas/Anteriores y tarjetas compactas de reservaciones y citas.
  • Soporte: seguro, análisis, recetas, médicos, dispositivos, billetera/suscripción e interacciones.
  • Tu cuenta: perfiles, solicitudes de seguidores, actividad con filtros por iconos y cierre de sesión.

El buscador superior conserva el campo vacío. Se incluyen los últimos ajustes de navegación y de diseño del calendario.

Integración en Laravel

  1. Use PHP 8.2+ y Laravel 12. Revise las dependencias de codigo/composer.json y el lockfile; incorpórelas al proyecto destino, conservando su propio composer.json. La API móvil utiliza Laravel Sanctum.
  2. Copie los archivos activos de codigo/resources/views/patient, el componente klini-icon y los recursos públicos manteniendo las rutas. Incorpore los bloques del layout original en el layout del destino. Las clases native-shell, patient-assistant-native-body y patient-portal-body forman parte del diseño.
  3. Integre el controlador, servicios, modelos y middleware conservando o adaptando sus namespaces. Las relaciones de Patient/User enlazan con modelos compartidos: por eso se incluyó su cierre de dependencias PHP.
  4. Copie integracion/routes/patient.php a su carpeta de rutas y cárguelo desde routes/web.php mediante require __DIR__.'/patient.php';. Registre el alias role para EnsureUserRole y el middleware web de páginas de sesión según su aplicación.
  5. Conserve las rutas con nombre patient.dashboard, patient.profile.update, patient.insurance.save, patient.appointments.store, patient.register_attachments.store y patient.register_attachments.download. El layout selecciona los estilos de paciente usando routeIs('patient.dashboard').
  6. El destino debe proporcionar home, login y logout. El cierre es POST con protección CSRF; termina la sesión y regresa a home. El acceso del destino debe autenticar un usuario relacionado con un Patient. No se entrega el acceso de revisión sin contraseña.
  7. Compare las migraciones de referencia/database/migrations con su esquema. Incluyen tablas compartidas de la plataforma y no son una migración autónoma del módulo. Adapte tablas, relaciones, archivos privados y auditoría antes de ejecutar las migraciones que correspondan.
  8. Después de integrar y configurar el entorno propio: ejecute composer install, php artisan optimize:clear y las pruebas enfocadas. Compruebe /patient con una sesión válida y un paciente de prueba.

Las rutas /images/..., /brand/... y /vendor/... son absolutas desde el origen del servidor. Si monta el módulo bajo un subdirectorio, adapte estos prefijos junto con las rutas de navegación y de carga/descarga.

Android / Flutter / React Native

Los adaptadores incluidos son puntos de entrada que abren el servidor existente. Configure su dominio HTTPS y el inicio de sesión web. El WebView necesita JavaScript y almacenamiento DOM para los controles actuales. Una sesión web usa cookies; un token Sanctum de la API no crea por sí mismo esa sesión.

  • Android: adaptadores/android/PatientWebViewActivity.kt. Requiere una aplicación AndroidX, permiso INTERNET y registrar la Activity. Incluye navegación básica y selección de archivos; integre las descargas autenticadas con la infraestructura de su app.
  • Flutter: adaptadores/flutter/patient_webview.dart. Añada webview_flutter y url_launcher. Ajuste selección/descarga de archivos según Android/iOS y su plugin.
  • React Native: adaptadores/react-native/PatientWebView.tsx. Añada react-native-webview y react-native-safe-area-context, con SafeAreaProvider en la aplicación anfitriona. Ajuste permisos y la integración de selección/descarga de documentos del proyecto destino.

Los adaptadores no se compilaron en SDKs Android/Flutter/React Native en esta entrega. Verifique en dispositivos: inicio/cierre de sesión, botón Atrás, teclado, adjuntos, permisos, enlaces externos, cámara cuando corresponda y descarga de documentos. El código Laravel del portal y sus recursos sí proceden de la versión local actual.

Fuentes oficiales: Android WebView, Flutter WebView, React Native WebView.

Si desea pantallas 100% nativas

Reutilice imágenes, colores, iconos y comportamiento como especificación; convierta el HTML a Views/Compose, widgets Flutter o componentes React Native. Los SVG inline deben convertirse al sistema de iconos de la plataforma. Reemplace el DOM, los eventos data-*, localStorage, los diálogos web y las directivas Blade por estado y componentes nativos.

La API opcional conserva el prefijo /api/mobile/v1. Sus rutas de paciente incluyen:

Consulte el contrato original en referencia/docs/openapi/klini-mobile-v1.yaml. También contiene endpoints de otros roles que se conservan como referencia, pero el fragmento de rutas entregado registra únicamente paciente y autenticación/sesiones/dispositivos compartidos. Integre los aliases, limitadores mobile-api/mobile-login, Gate y manejo JSON del bootstrap/proveedor de referencia. La API actual no reemplaza todavía todas las funciones web: por ejemplo, reservar una cita se realiza por la ruta web y no existe en este paquete un CRUD de actividad social multiusuario.

Datos y recursos

Perfil principal, citas médicas, seguro, prescripciones, historial y documentos se obtienen del backend. Comunidades, solicitudes sociales, perfiles alternos, favoritos y registros manuales contienen comportamiento local/demostración almacenado por perfil en el navegador. Cambiar de dominio o de WebView no traslada automáticamente ese almacenamiento.

No se incluyen base de datos, .env, sesiones, cookies, logs, archivos clínicos cargados ni datos extraídos del navegador. Las fotos y catálogos de demostración definidos en código forman parte de los recursos visuales. RECURSOS-EXTERNOS.json registra las imágenes remotas y si están empaquetadas. Cuando se descargan, las copias exportadas apuntan a /images/patient-export/; los originales se conservan en referencia/originales-con-enlaces-remotos/.

Se conservan las licencias de fuentes/iconos y la procedencia de los recursos existentes. El diseño funciona con datos del servidor: no abra una plantilla Blade como un HTML estático esperando obtener el módulo completo.
